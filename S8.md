# S8 — Prompt para Frontend: Gestión de Usuarios (Admin)

## Objetivo
Proveer al equipo frontend un prompt claro para implementar una interfaz donde los administradores puedan ver la lista de usuarios y eliminar usuarios.

## Requisitos funcionales (para el frontend)
- Mostrar una tabla/lista con los usuarios del sistema: `id`, `email`, `role`, `is_active`, `digital_signature_path`.
- Solo usuarios con rol `admin` deben poder ver la lista y los botones de eliminación.
- Usar autenticación Bearer (token JWT) en la cabecera `Authorization: Bearer <token>` obtenida tras login.
- Confirmación modal antes de eliminar un usuario.
- Tras eliminar, refrescar la lista y mostrar notificación de éxito/errores.
- Manejar estados: carga, vacío, error y confirmación.

## Especificación de llamadas HTTP
- Obtener lista de usuarios (requiere admin):
  - Método: `GET`
  - Ruta: `/api/v1/auth/users`
  - Headers: `Authorization: Bearer <access_token>`
  - Respuesta: `200 OK` con array de usuarios (cada usuario cumple `UserResponse`).

- Eliminar usuario (requiere admin):
  - Método: `DELETE`
  - Ruta: `/api/v1/auth/users/{user_id}`
  - Headers: `Authorization: Bearer <access_token>`
  - Respuesta: `204 No Content` en caso de éxito.

- Cambiar rol de usuario (requiere admin):
  - Método: `PATCH`
  - Ruta: `/api/v1/auth/users/{user_id}/role`
  - Headers: `Authorization: Bearer <access_token>`
  - Body (JSON): `{ "role": "admin" }` o `{ "role": "user" }`
  - Respuesta: `200 OK` con el `UserResponse` actualizado.

## UX / Comportamiento sugerido
- Componente `UserManagement`:
  - Al montar: solicitar `GET /api/v1/auth/users`.
  - Tabla con columnas: `Email`, `Rol`, `Activo`, `Acciones`.
  - Columna `Acciones`: botón `Eliminar` visible solo si el usuario actual es admin.
  - Al pulsar `Eliminar`: abrir modal de confirmación con el email del usuario.
  - Confirmar → llamar `DELETE /api/v1/auth/users/{id}`. Si `204`, cerrar modal y recargar la lista.
  - Mostrar toasts para éxito y errores.

  Integración para cambiar rol:

  - Añadir un control en la fila (por ejemplo un `select` con `user|admin`) visible solo para admins.
  - Al cambiar la opción, mostrar modal de confirmación: "Cambiar rol de <email> a <nuevo_rol>?".
  - Confirmar → llamar `PATCH /api/v1/auth/users/{id}/role` con body `{ "role": "admin" }`.
  - Si la respuesta es `200`, actualizar la fila localmente y notificar éxito; en caso de error mostrar mensaje.

## Ejemplo de implementación (pseudocódigo JS)

- Obtener token (ejemplo):
```
const token = localStorage.getItem('access_token');
const headers = { 'Authorization': `Bearer ${token}`, 'Content-Type': 'application/json' };
```

- Cargar usuarios:
```
const res = await fetch('/api/v1/auth/users', { headers });
if (res.ok) users = await res.json(); else handleError();
```

- Eliminar usuario:
```
const res = await fetch(`/api/v1/auth/users/${id}`, { method: 'DELETE', headers });
if (res.status === 204) showSuccess(); else showError();
```

// Cambiar rol:
```
const res = await fetch(`/api/v1/auth/users/${id}/role`, {
  method: 'PATCH',
  headers,
  body: JSON.stringify({ role: 'admin' })
});
if (res.ok) {
  const updated = await res.json();
  // actualizar UI
} else {
  // manejar error
}
```

## Seguridad y validaciones
- El frontend no debe confiar en la UI para controlar permisos: siempre incluir el token en las llamadas; el backend valida rol.
- Manejar errores 401/403 redirigiendo a login o mostrando mensaje de permisos.

# Resumen de endpoints creados (backend)

- `POST /api/v1/auth/create-admin` — Crea un usuario con rol `admin`. Requiere token de un admin existente. Respuesta: `201 Created` con `UserResponse`.

- `DELETE /api/v1/auth/users/{user_id}` — Elimina un usuario por ID. Requiere token de admin. Respuesta: `204 No Content`.

- `GET /api/v1/auth/users` — Lista todos los usuarios. Requiere token de admin. Respuesta: `200 OK` con arreglo de `UserResponse`.

> Nota: Para integrar la UI, el frontend debe usar `Authorization: Bearer <token>` obtenido del login.
